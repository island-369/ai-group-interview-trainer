# 02 · 系统架构设计

> 版本：v0.1 ｜ 日期：2026-10-24 ｜ 上游：[01-需求分析](01-需求分析.md) ｜ 下游：[04-设计方案](04-设计方案.md)

## 1. 架构总览

五层架构：前端层 / 接入层 / 业务编排层 / 智能体层 / 模型服务层，下接数据层。

```
┌──────────────────────────────────────────────────────────────────┐
│                          前端层 Web (Next.js)                     │
│   训练大厅/对局配置 · 对局室(多方实时) · 复盘报告 · 训练记录 · 题库   │
└─────────────────────────────┬────────────────────────────────────┘
                        HTTPS / WSS
┌─────────────────────────────┴────────────────────────────────────┐
│                        接入层 (FastAPI)                           │
│     REST：对局配置/题库/报告/记录    WS：对局室实时消息路由           │
└─────────────────────────────┬────────────────────────────────────┘
┌─────────────────────────────┴────────────────────────────────────┐
│                         业务编排层                                 │
│  SessionManager      对局生命周期、阶段状态机、计时、断线恢复         │
│  AgentOrchestrator   导演调度：发言意愿/抢话/冷场/剧情事件           │
│  EvaluationEngine    评估管线（行为切分→评分→报告），对局后异步执行    │
│  QuestionBank        题库与抽题；TrainingProfile 训练记录/成长曲线   │
└──────────────┬───────────────────────────────────────────────────┘
┌──────────────┴───────────────────────────────────────────────────┐
│                          智能体层                                  │
│  InterviewerAgent 面试官 · CandidateAgent × N 候选人(人格化)        │
│  DirectorAgent 导演(不发言,只决策) · EvaluatorAgent 评估            │
│  CoachAgent 教练提示(P1) · QuestionGeneratorAgent 出题(P1)         │
└──────────────┬───────────────────────────────────────────────────┘
┌──────────────┴───────────────────────────────────────────────────┐
│                         模型服务层                                 │
│  LLM Gateway：多模型路由 / 流式 / 重试降级 / 并发与token预算 / 缓存  │
│  ASR / TTS（M3 语音对局引入，接口预留）                             │
└──────────────┬───────────────────────────────────────────────────┘
┌──────────────┴───────────────────────────────────────────────────┐
│  数据层  SQLite(开发) → PostgreSQL(生产) + 对象存储(报告附件/音频)    │
│  users · questions · sessions · session_members · messages         │
│  director_logs · reports · score_details · training_records        │
└───────────────────────────────────────────────────────────────────┘
```

分层职责边界：编排层**只管流程与调度**，不含扮演逻辑；智能体层**只管生成**，不感知网络与存储；所有 LLM 调用必须经 Gateway，不允许智能体直连模型。

## 2. 核心架构决策（ADR）

### ADR-1 采用"导演-演员"集中编排，而非去中心化自由对话

- **问题**：N 个 AI 自由对话极易出现轮流发言、过度礼貌、抢话混乱三种失真，且难以调难度。
- **决策**：引入不发言的 DirectorAgent 集中决策"下一个谁发言、是否允许打断、何时推进剧情"；CandidateAgent 只在被调度时生成内容。
- **理由**：拟真度问题本质是**调度问题**而非**内容问题**；集中化后难度、节奏、剧情全部可控可调，也便于回放复现与回归测试。
- **备选方案**：AutoGen/CrewAI 等自由多智能体框架 —— 交互节奏不可控、评估复现困难，放弃（可复用其部分工具链思想）。

### ADR-2 文本先行，语音后置（M3）

- **理由**：核心价值假设（拟真对局+评估反馈）用文本即可验证；语音引入 ASR/TTS/打断延迟等工程复杂度，先验证再投入。

### ADR-3 自研轻量编排 + 统一 LLM Gateway

- **决策**：不深度依赖重型 Agent 框架；编排层自研（状态机 + 调度器共约数千行），模型访问统一走 Gateway。
- **理由**：群面场景的核心逻辑（意愿调度、抢话、评分）高度定制，框架抽象收益低、约束高；Gateway 保证模型可替换（GLM/GPT/本地模型）与成本可控（龙套角色降级到小模型）。

### ADR-4 对局用 WebSocket 单连接消息流；评估离线异步

- **决策**：对局期间所有事件（发言流、打断、阶段变更）走一条 WS 按 JSON 消息推送；评估在对局结束后由后台任务执行，前端轮询/通知获取报告。
- **理由**：避免把评分逻辑塞进实时链路拖慢节奏；评估可以多次采样换取稳定性。

### ADR-5 数据先 SQLite 后 PostgreSQL，表结构不变

- 单机 MVP 零运维；对局数据天然按 session 分片，未来水平扩展路径清晰（05§9）。

## 3. 对局运行时设计

### 3.1 阶段状态机

```
INIT → BRIEFING → READING → OPENING → DISCUSSION → SUMMARY → CLOSING → REVIEW(离线)
 配置    宣题/规则   独立阅读    个人陈述     自由讨论     总结陈词    收尾      报告生成
```

| 阶段 | 进入条件 | 系统行为 | 流转触发 |
|------|----------|----------|----------|
| INIT | 创建对局 | 生成 AI 人格组合、注入剧本大纲 | 用户 ready |
| BRIEFING | — | InterviewerAgent 宣读题目与规则 | 定长（~1min） |
| READING | — | 用户可看材料、写笔记；AI 并行生成"个人立场笔记"（不外显） | 定长（3–5min，可缩短） |
| OPENING | — | 按（可配置）顺序每人限时陈述；AI 间不插话 | 全员完成/超时 |
| DISCUSSION | — | **导演调度核心区**：意愿竞争、抢话、剧情、冷场处理 | 总时长到 or 全组共识（导演判定） |
| SUMMARY | — | 开放"争取总结"发言 → 导演指定/竞得者陈词；其他 AI 可补充 | 陈词完成 |
| CLOSING | — | 面试官收尾 | 自动 |
| REVIEW | 对局关闭 | EvaluationEngine 异步跑评估管线，生成报告 | 完成后通知 |

状态机由 SessionManager 持有；所有流转事件写入 messages（kind=phase），保证回放完整。

### 3.2 导演调度循环（运行时心脏）

```
每个决策窗口（上一发言结束后 0.8–2.5s 随机抖动）：
  1. 收集上下文：阶段、剩余时间、各 agent 状态、剧情队列
  2. if 阶段 == OPENING：按顺序轮流（跳到用户则等待其发言或超时）
  3. if 阶段 == DISCUSSION：
       a. 计算每个空闲 agent 的发言意愿 desire_i（公式见 04§5.3）
       b. 用户保护窗口：用户正在输入/发言时，AI 不强行覆盖（可被打断档位除外）
       c. 若 max(desire) < 冷场阈值 且持续 T 秒 → 冷场处理：
            面试官推进 / 点名沉默者 / 触发剧情事件
       d. 若 top1 与 top2 意愿差 < ε 且双方激进度高 → 抢话竞争事件
       e. 选定发言者 → 流式生成 → 发言分多段，段间为"可打断窗口"，
          窗口内检查其他 agent 的 interrupt_desire，触发则执行打断协议
  4. 剧情检查：每 K 轮评估剧情队列，到期注入（冲突升级/集火用户/跑题/时间压力…）
  5. 记录 director_log（决策依据快照，供复盘与回归测试）
```

关键约束：**同一时刻至多一个发言者**（单写者原则）；"打断"实现为被打断者收到事件后按人格决定让出/压缩收尾（详见 04§5.3），避免并发写消息流导致体验混乱。

### 3.3 消息流

```
用户浏览器 ──user_speak──▶ WS ──▶ SessionManager(写入 messages)
                                   │
                                   ▼
                          AgentOrchestrator(导演决策)
                                   │ 调度结果
                                   ▼
                    CandidateAgent/InterviewerAgent ──▶ LLM Gateway(流式)
                                   │ speak_chunk…
                                   ▼
                          WS 推送 ──▶ 所有客户端（含发起者）
```

对局运行时（Session Runtime）= 单个 asyncio Task 组：1 个导演循环 + N 个按需唤醒的 agent 生成任务 + 1 个计时器。一个进程可承载多场对局（MVP 单进程足够）。

## 4. 智能体层职责

| Agent | 数量 | 是否发言 | 职责 | 模型策略 |
|-------|------|----------|------|----------|
| InterviewerAgent | 1 | 是 | 宣题、规则、时间提醒、控场干预、压力面（高难度档） | 主模型，调用次数少 |
| CandidateAgent | 3–7 | 是 | 人格化扮演候选人：陈述、讨论、抢话、被抢后的反应、争取总结 | 主模型为主；低重要度龙套角色可降级小模型 |
| DirectorAgent | 1 | 否 | 发言意愿评估、调度、剧情注入、冷场处理、共识判定 | 规则引擎为主 + 小模型辅助判断（话题相关度/共识度） |
| EvaluatorAgent | 1（离线） | 否 | 8 维度评分（带证据）、逐句标注、名次、改进建议 | 主模型，temp=0，多次采样 |
| CoachAgent | 0–1 | 否（仅对用户） | 卡壳检测、方向性提示（P1） | 小模型即可 |

Director 的意愿计算大部分是规则（人格参数 + 状态），只有"话题相关度/共识判定"用小模型打分，控制成本与延迟。

## 5. 数据架构

### 5.1 ER 概览

```
users 1──* sessions *──1 questions
sessions 1──* session_members（user/ai/interviewer 角色，ai 挂 persona JSON）
sessions 1──* messages（发言/打断/阶段/系统事件，seq 全序）
sessions 1──* director_logs（每轮调度决策快照）
sessions 1──1 reports 1──* score_details（维度×分数×证据）
users 1──* training_records（维度分数时序，支撑成长曲线）
```

设计要点：
- **messages 全序单表**：所有事件（含打断、阶段流转）统一带 seq 写入，回放 = 按 seq 重放，评估输入 = 该表导出转录；
- **director_logs**：保存每轮 desire 值与决策理由，用于（a）复盘解释"AI 为什么那时抢话"（b）prompt 回归测试固定回放；
- **persona 以 JSON 存于 session_members**：人格卡模板在代码库 YAML 中，实例化时快照进对局，保证历史对局不受后续人格改动影响。

DDL 详见 [05-实现方案](05-实现方案.md)§3。

### 5.2 存储选型

SQLite（开发/单机）→ PostgreSQL（生产）；报告原文与未来音频走对象存储/本地文件。无 Redis 依赖（MVP 计时用进程内定时器；多机部署时引入 Redis 做会话路由，见 §8）。

## 6. 接口设计

### 6.1 REST（摘要）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/questions?type=&industry= | 题库查询 |
| POST | /api/sessions | 创建对局（配置校验、人格组合生成），返回 session_id + ws url |
| GET | /api/sessions/{id} | 对局详情（含成员人格卡） |
| GET | /api/sessions/{id}/transcript | 转录（回放） |
| GET | /api/sessions/{id}/report | 报告（未生成返回 202 + 预估时间） |
| GET | /api/trainings/summary | 成长曲线数据 |

### 6.2 WS 消息协议（摘要，完整定义见 04§4）

下行：`phase / speak_start / speak_chunk / speak_end / interrupt / interviewer / coach / error`
上行：`user_ready / user_typing / user_speak / user_note`

消息均带 `session_id`、`ts`、`seq`（下行全序号），断线重连后按 seq 补发。

## 7. 评估管线架构（对局后离线）

```
messages(转录) ─▶ ① 行为事件切分（发言/打断/沉默/引用/反驳…）
             ─▶ ② 逐维度评分（EvaluatorAgent，每次调用只评 2 个维度，
                  强制引用证据原文，temp=0，采样 3 次取中位数）
             ─▶ ③ 一致性仲裁（分数与证据矛盾检测；分歧>1分维度二次仲裁）
             ─▶ ④ 汇总生成：总分/名次/雷达图/优势短板/改进动作/逐句标注
             ─▶ 写入 reports + score_details，通知前端
```

把"逐维度"拆成小任务而非一次评全部：单次调用上下文可控、证据密度高、分数更稳；代价是调用次数多，离线场景可接受。

## 8. 部署与扩展路径

```
MVP：单机 Docker Compose（web + server + sqlite卷）—— 支撑数百用户足够
  ↓ 对局是长连接有状态服务
水平扩展（需要时）：网关按 session_id 粘性路由；Session Runtime 独立成 worker 池；
  Redis 承担会话路由表 + 跨节点事件总线；评估走任务队列（Celery/Arq）天然横向扩展
```

模型层扩展：Gateway 支持按 agent 角色路由不同模型/供应商；评估与主角 candidate 用强模型，龙套与导演辅助判断用轻量模型。

## 9. 安全与隐私

- 对局内容仅本人可见；报告与转录支持一键删除（级联）；
- LLM Gateway 出站统一脱敏钩子（可选开启：擦除手机号/邮箱等）；
- WS 鉴权：短期 token 绑定 session；REST 常规鉴权；
- 预算熔断：单场/单日 token 预算超限自动降级模型或终止对局并提示。
